# bazis-bg 2.6.0

Requires bazis 2.16 (`bazis.core.declare`).

## Changes

- **Periodic tasks declared in the code.** `SCHEDULES = [Schedule(slug, task, period,
  name=None, kwargs={}, enabled=True)]` in the `schedules.py` module of an application
  (`bazis.contrib.bg.declare`) is applied by `migrate` (`post_migrate`, also sent by
  `flush`) once all the migrations are applied, in one transaction under the advisory
  lock of the declarations: the periodic task (`TaskCron`) of each slug is created or
  updated as declared and marked `managed`; a new period or `enabled` resets its next run
  time. An unmarked periodic task of the slug (made in the admin) is taken over with a
  warning; a managed one no longer declared is disabled and becomes an ordinary one (not
  deleted; the admin may enable it again, unlike the roles and transits, which stay
  managed). The name is stored translated into `LANGUAGE_CODE`. A data migration with
  `get_or_create` applied a period only once.
- `TaskCron` has the fields `slug` (unique, optional) and `managed` (the migration
  `0006_taskcron_slug_managed`).
- System checks: `bg.E001` (the slug, a duplicate, the name, the period: positive seconds
  or a valid cron expression, the kwargs: JSON without the reserved `name`, `fp`,
  `author`, `envs`, `enabled`), `bg.E002` (the task class imports, is a `BgBase` with a
  name, and its `__init__` takes the kwargs) and the database check `bg.W001` (the
  database differs from the declarations), `bg.W002` (an enabled periodic task that is
  not managed runs the task of a schedule with its kwargs: both would run; delete it).
- The admin shows a declared periodic task read-only besides `dt_run` and `envs`
  (`bazis.core.admin_abstract.ManagedAdminMixin`) and does not delete it.
- `bazis_test_utils` 2.5.2 applies the schedules in `apply_declarations()` and the
  fixture `bazis_declared`.
- The guide describes the declaration instead of "in the admin or in code".
- **The files of the tasks are private.** An export was stored as
  `bg/<file_name>.<time to the second>.xlsx`: the media host, which serves `MEDIA_ROOT`
  without a check, gave its personal data to whoever guessed the time. A task file
  (an export, a fixture, a file given as `delay(fp=...)`) is now stored as
  `<BAZIS_TASK_FOLDER>/<token>_<name>` with a random token (`secrets.token_urlsafe(16)`),
  and `GET /api/v1/bg/task/{id}/download/` (`BgRoute.action_download`) serves it to the
  author of the task and staff (the rule of `restrict_queryset`): 401 for an anonymous
  user, 404 for another user's task, a task without a file or a file missing from the
  storage; always a download named after the file without its token, with `nosniff`,
  `Content-Security-Policy: sandbox` and `Cache-Control: private, no-store`.

## Upgrading

- Download the file of a task from `/api/v1/bg/task/{id}/download/` instead of the `file`
  attribute: the attribute is still the URL of the media host (not breaking), which serves
  the file to anyone who has the link. A custom task route that lists its `actions` adds
  `'action_download'`.
- The files stored before the upgrade keep their guessable names until the cleanup task
  deletes them (`BAZIS_TASK_LIFETIME`): delete the old exports in `MEDIA_ROOT/bg/` that are
  no longer needed.
- The stored name is 23 characters longer: the storage shortens the name of an export
  whose `file_name` is longer than about 50 characters (`max_length` 100 of `Task.file`;
  before, about 70).

### Periodic tasks made before the declarations

A periodic task created by a `get_or_create` data migration or in the admin has no slug:
declared in `schedules.py` as it is, it would run twice (`bg.W002`). Delete the old row and
let the declaration own the schedule: in the admin, or with a data migration of the
product that depends on the old one and on `('bg', '0006_taskcron_slug_managed')` (it
works whether `migrate` has already created the declared row or not):

```python
def delete_old_cron(apps, schema_editor):
    apps.get_model('bg', 'TaskCron').objects.filter(
        cls_path='training.bg.deadlines.RemindDeadlines', slug=None,
    ).delete()
```

The tasks the old row started are kept, no longer linked to a periodic task
(`on_delete=SET_NULL`), and the cleanup counts them as manual tasks.
