# bazis-bg 2.6.0

Requires bazis 2.16 (`bazis.core.declare`) and bazis-users 2.9 (a direct dependency now:
`BgRoute.restrict_queryset` takes its user from `UserMixin.authenticated_user`). The
`test` extra requires bazis-test-utils 2.5.2, whose plugin applies the schedules and
installs the triggers of the test database.

## Changes

- **Periodic tasks declared in the code.** `SCHEDULES = [Schedule(slug, task, period,
  name=None, kwargs={}, enabled=True)]` in the `schedules.py` module of an application
  (`bazis.contrib.bg.declare`) is applied by `migrate` (`post_migrate`, also sent by
  `flush`) once all the migrations are applied, in one transaction under the advisory
  lock of the declarations: the periodic task (`TaskCron`) of each slug is created or
  updated as declared and marked `managed`; a new period or `enabled` resets its next run
  time. An unmarked periodic task of the slug (made in the admin) is taken over with a
  warning; a managed one no longer declared is disabled and becomes an ordinary one (not
  deleted; the admin may enable it again, unlike the roles and transits, which stay
  managed). The name is stored translated into `LANGUAGE_CODE`. A data migration with
  `get_or_create` applied a period only once.
- `TaskCron` has the fields `slug` (unique, optional) and `managed` (the migration
  `0006_taskcron_slug_managed`).
- System checks: `bg.E001` (the slug, a duplicate, the name, the period: positive seconds
  or a valid cron expression, the kwargs: JSON without the reserved `name`, `fp`,
  `author`, `envs`, `enabled`), `bg.E002` (the task class imports, is a `BgBase` with a
  name, and its `__init__` takes the kwargs) and the database check `bg.W001` (the
  database differs from the declarations), `bg.W002` (an enabled periodic task that is
  not managed runs the task of a schedule with its kwargs: both would run; delete it).
- The admin shows a declared periodic task read-only besides `dt_run` and `envs`
  (`bazis.core.admin_abstract.ManagedAdminMixin`) and does not delete it.
- `bazis_test_utils` 2.5.2 applies the schedules in `apply_declarations()` and the
  fixture `bazis_declared`.
- The guide describes the declaration instead of "in the admin or in code".
- The name of a task class and the names of its phases may be lazy texts (the guide says
  in which language a task stores them). A phase is stored as text when it starts
  (`next_phase`): its record in `phases_history` was written in the language active when
  the phase ended.
- **The files of the tasks are private.** An export was stored as
  `bg/<file_name>.<time to the second>.xlsx`: the media host, which serves `MEDIA_ROOT`
  without a check, gave its personal data to whoever guessed the time. A task file
  (an export, a fixture, a file given as `delay(fp=...)`) is now stored as
  `<BAZIS_TASK_FOLDER>/<token>_<name>` with a random token (`secrets.token_urlsafe(16)`),
  and `GET /api/v1/bg/task/{id}/download/` (`BgRoute.action_download`) serves it to the
  author of the task and staff (the rule of `restrict_queryset`): 401 for an anonymous
  user, 404 for another user's task, a task without a file or a file missing from the
  storage; always a download named after the file without its token, with `nosniff`,
  `Content-Security-Policy: sandbox` and `Cache-Control: private, no-store`.
- The guide is read by sections: its introduction maps them with when to read each (bazis-mcp
  serves it alone), and the items of the manifest are one line each, their details in the
  guide; the exports and imports have a section of their own.
- The health check server of `bg_handler` and `bg_scheduler` is
  `bazis.contrib.bg.network` (`check_port`, `healthcheck_server`), moved from
  `bazis.core.utils.network`, and bazis-bg requires `aiohttp` itself: bazis 2.16 no longer
  depends on it. The module of the core re-exports it with a `DeprecationWarning` until
  Bazis 3.0.

- **The cleanup of the tasks runs by default.** bazis-bg declares the periodic task
  `bg_tasks_clean` (`bazis/contrib/bg/schedules.py`), which `migrate` applies: it deletes
  the manual tasks not updated for `BAZIS_TASK_LIFETIME` (90 days) and the periodic ones
  not updated for `BAZIS_TASK_CRON_LIFETIME` (6 hours), with their files, every
  `BAZIS_TASK_CRON_CLEANUP` seconds. Before, it ran only in the projects that had run
  `manage.py cleanup_init` (none of the known ones), so the tasks and the exports with
  their personal data were kept for ever, and the command created the periodic task once
  (`get_or_create`): a new period never reached it. The migration
  `0007_taskcron_clean_declared` makes the periodic task of `cleanup_init` the declared
  one, so the cleanup does not run twice. `BAZIS_TASK_CRON_CLEANUP` is no longer a dynamic
  setting (`migrate` applies it, an admin value never reached the periodic task); the new
  `BAZIS_TASK_CLEANUP` (true) turns the cleanup off.

- **The admin templates of bazis-bg no longer replace those of the project.** The package
  shipped `admin/base.html`, which rendered every message of the admin of the project
  without escaping (`safe`), and `admin/change_list.html` and `admin/pagination.html` for
  all the models. The message of a started task is built with `format_html` (the name of
  the task is escaped); the change list of `LoadDownloadAdminMixin` is its own
  `change_list_template` (`admin/bg/change_list.html`), and the other models get the
  templates of Django. `file_load.js` is plain JavaScript: the copy of jQuery 3.5.1 that
  the admin loaded next to the jQuery of Django is removed.

## Upgrading

- An admin class with `LoadDownloadAdminMixin` and a `change_list_template` of its own
  extends `admin/bg/change_list.html` in that template: the file field of the load actions
  needs it.
- The cleanup deletes the tasks older than the lifetimes at its first run after the
  upgrade: set `BS_BAZIS_TASK_LIFETIME` (seconds) to keep them longer, or
  `BS_BAZIS_TASK_CLEANUP=false` to keep them all (also where the periodic task of
  `cleanup_init` was disabled in the admin: the declaration enables it). A value of
  `BAZIS_TASK_CRON_CLEANUP` saved in the admin is ignored: set `BS_BAZIS_TASK_CRON_CLEANUP`.
- `manage.py cleanup_init` does nothing and is removed in 2.7: remove it from the deploy
  scripts.

- Download the file of a task from `/api/v1/bg/task/{id}/download/` instead of the `file`
  attribute: the attribute is still the URL of the media host (not breaking), which serves
  the file to anyone who has the link. A custom task route that lists its `actions` adds
  `'action_download'`.
- The files stored before the upgrade keep their guessable names until the cleanup task
  deletes them (`BAZIS_TASK_LIFETIME`): delete the old exports in `MEDIA_ROOT/bg/` that are
  no longer needed.
- The stored name is 23 characters longer: the storage shortens the name of an export
  whose `file_name` is longer than about 50 characters (`max_length` 100 of `Task.file`;
  before, about 70).

### Periodic tasks made before the declarations

A periodic task created by a `get_or_create` data migration or in the admin has no slug:
declared in `schedules.py` as it is, it would run twice (`bg.W002`). Delete the old row and
let the declaration own the schedule: in the admin, or with a data migration of the
product that depends on the old one and on `('bg', '0006_taskcron_slug_managed')` (it
works whether `migrate` has already created the declared row or not):

```python
def delete_old_cron(apps, schema_editor):
    apps.get_model('bg', 'TaskCron').objects.filter(
        cls_path='training.bg.deadlines.RemindDeadlines', slug=None,
    ).delete()
```

The tasks the old row started are kept, no longer linked to a periodic task
(`on_delete=SET_NULL`), and the cleanup counts them as manual tasks.

## Removed

Nothing in the Bazis packages and the known products used them:

- `bazis.contrib.bg.utils` (`XlsxReader`): the imports read xlsx and zip files with
  `BgBaseLoad`.
- The setting `BAZIS_TASK_HANDLERS_GLOBAL`: nothing read it; the number of handlers is
  `BAZIS_TASK_HANDLERS_LOCAL` per scheduler.
- `bazis.contrib.bg.admin_tags.task_is_run` (it failed: a task has no `cls` field) and
  `task_is_success` (`Task.is_success`).
