# bazis-bg 2.6.0

Requires bazis 2.16 (`bazis.core.declare`).

## Changes

- **Periodic tasks declared in the code.** `SCHEDULES = [Schedule(slug, task, period,
  name=None, kwargs={}, enabled=True)]` in the `schedules.py` module of an application
  (`bazis.contrib.bg.declare`) is applied by `migrate` (`post_migrate`, also sent by
  `flush`) once all the migrations are applied, in one transaction under the advisory
  lock of the declarations: the periodic task (`TaskCron`) of each slug is created or
  updated as declared and marked `managed`; a new period or `enabled` resets its next run
  time. An unmarked periodic task of the slug (made in the admin) is taken over with a
  warning; a managed one no longer declared is disabled and becomes an ordinary one (not
  deleted; the admin may enable it again, unlike the roles and transits, which stay
  managed). The name is stored translated into `LANGUAGE_CODE`. A data migration with
  `get_or_create` applied a period only once.
- `TaskCron` has the fields `slug` (unique, optional) and `managed` (the migration
  `0006_taskcron_slug_managed`).
- System checks: `bg.E001` (the slug, a duplicate, the name, the period: positive seconds
  or a valid cron expression, the kwargs: JSON without the reserved `name`, `fp`,
  `author`, `envs`, `enabled`), `bg.E002` (the task class imports, is a `BgBase` with a
  name, and its `__init__` takes the kwargs) and the database check `bg.W001` (the
  database differs from the declarations), `bg.W002` (an enabled periodic task that is
  not managed runs the task of a schedule with its kwargs: both would run).
- The admin shows a declared periodic task read-only besides `dt_run` and `envs`
  (`bazis.core.admin_abstract.ManagedAdminMixin`) and does not delete it.
- `bazis_test_utils` 2.5.2 applies the schedules in `apply_declarations()` and the
  fixture `bazis_declared`.
- The guide describes the declaration instead of "in the admin or in code".

## Upgrading

A periodic task created by a `get_or_create` data migration or in the admin has no slug:
declared in `schedules.py` as it is, it would run twice (`bg.W002`). Give its row the slug
of the schedule before the schedules are applied, so that `migrate` takes it over and keeps
its tasks: in the admin, or in a data migration of the product that depends on the old one
and on `('bg', '0006_taskcron_slug_managed')`:

```python
apps.get_model('bg', 'TaskCron').objects.filter(
    cls_path='training.bg.deadlines.RemindDeadlines', slug=None,
).update(slug='deadlines_remind')
```

Or delete the row (in the admin, or with a data migration in place of the old one).
