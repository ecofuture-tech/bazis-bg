# bazis-bg 2.7.0

Requires the same versions as 2.6.0 (bazis 2.16, bazis-author 2.5, bazis-users 2.9).

## Changes

- **The author of a task no longer reads its traceback and log.** The task route
  (`GET /api/v1/bg/task/`, `/{id}/`) gave the author of a task its `error`, the full
  traceback written by the handler (`traceback.format_exc()`), and its `log`: paths and code
  of the server and data of the message (a database error quotes the row). For a user who
  is not staff, `error` is now `Error` and `log` is null; a task without an error (null or
  empty) keeps it, so `error` still tells a failed task. No part of the text is given, not
  even the class of the exception: a message may quote anything, a traceback included, so
  a class read from the text could be a word of the message. The filter and the sorting of the route no longer reach
  `error` and `log` for such a user (a filter by their text would read them), also through
  a relation of another route (`filter=task__error__...`). Staff read both as before; the
  stored task is not changed.
- **`task_accepted(task)`** (`bazis.contrib.bg.routes`): the answer of an action that
  queued a task, 202 with `{"data": {"type": "bg.task", "id": "<id>"}}` and the URL of the
  task as `Location` (`/api/v1/bg/task/<id>/`), which the client (the task progress
  component of bazis-front) polls until the task is done. The sample route of the reports
  has such an action (`POST /api/v1/entity/report/calc/`).
- The guide has the section "Following a task from a client" (and the README a
  subsection): the action, the fields a client reads, and the progress of the phases:
  `expected` and `performed` are those of the current phase and are set to null when it
  ends, its record moving to `phases_history` (`{phase, duration, expected, performed}`),
  so they are null once the task is done.

## Upgrading

- A client that showed `error` or `log` of a task to its author gets `Error` and no log:
  show a message of its own for a failed task, and let staff (or the admin) read the
  traceback. A cause the author must see is a field of the product (the task writes a
  message it chooses with `set_result`). A client that filtered or sorted the tasks by `error` or `log`
  for such a user gets 400 `ERR_FILTER`.
- A custom task route subclasses `BgRoute` to keep the rule. A product route that includes
  `task` (`include=task`) still gives the tasks as loaded, traceback and log included: the
  core has no hook for the items of `included`. Do not include the tasks for users who are
  not staff; the client reads them at the task route.
